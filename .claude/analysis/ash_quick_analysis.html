Overall

This is high-quality work. Correctness and security have had real attention, the design is consistent, and the tests back it up. I would trust it in the application it came from.

The honest weaknesses are about size and reach, not bugs. It does a great deal, it changes your schema on opt-in, it is configured globally, its hardest logic sits in a few very large modules, and one person maintains all of it.

Aspect 1

Scope

The name says "CRUD LiveViews", but the package is closer to an application platform: it also owns auditing, optimistic locking, bookkeeping columns, file storage, PDF printing, navigation, impersonation and browser-session tracking. The breadth is coherent because it was extracted from one production app, and that is also its main cost for anyone else adopting it.

LayerWhat it owns
Resource extension10 DSL sections: liveness, display, labels, forms, lookup, activation, versioning, bookkeeping, audit, read_only_fields
Web layerQuickView (list, details, create, update), filters, sorting, bulk actions, action modal, export (CSV, Excel), print (ChromicPDF)
Host seamsScope, Storage (S3, S3 proxy, local disk), AccessControl, Nav, PrintTemplate, ReadOnlyFields.Check
OperationsInstaller and generators (Igniter), mix ash_quick.check, Tower error reporting, gettext catalogue, timezones, browser sessions
Strong

Every host dependency is a named seam

Actor, tenant, storage, route access, navigation and print templates are each a behaviour or a config key, not an assumption about the host. For a library pulled out of an app, that discipline is the hard part and it has been done.

Strong

Optional features are optional dependencies

CSV, Excel, PDF, S3, Money and Igniter are all optional: true, and the feature is absent without them, not broken. The core install stays at Ash, AshPhoenix, Spark, Phoenix LiveView, gettext, live_select, jason and tower.

Could be better

One opt-in line changes the database schema

extensions: [AshQuick] adds a version column, timestamps and two actor foreign keys, attaches an audit change to every write, and wires PubSub. The README says so clearly, but a UI library that migrates your tables on opt-in is a large commitment. Versioning, bookkeeping and audit are each useful without any LiveView, and a LiveView is useful without them. Splitting them into separately adoptable extensions (even inside one package) would let someone try the UI on an existing resource without a migration.

Could be better

Several subsystems are libraries in their own right

Storage with three backends and an S3 proxy (about 1,900 lines), audit (about 1,500), browser-session presence, timezone handling and the nav registry have little to do with rendering CRUD. Each one widens the surface you must keep secure and compatible. If the goal is public adoption, the candidates to extract first are storage and audit, since both have value to people who never use a QuickView.

Could be better

Hard requirements that narrow the audience

Elixir 1.19 as the floor, Tower as a required error reporter, and live_select as a required UI dependency are all defensible for the source app. For a 0.1.0 trying to find users they are three reasons to bounce. Tower in particular could be a behaviour with Tower as the default adapter.

Note

The resource contract is strict

A resource needs an :id that addresses one row and a display label, or it does not compile. Composite-key resources are excluded. This is a reasonable trade for a declarative tool, and failing at compile time is the right place to fail.

Aspect 2

Design

The architecture is sound and idiomatic for the Ash ecosystem: a Spark extension that fails at compile time, a macro that stays thin, and behaviours at every boundary. The weak spots are a wide configuration surface, a single very large use options contract, and event handling that is spread across hooks and so is harder to follow than it needs to be.

Strong

Compile-time verification is the central idea, and it is applied consistently

Nine transformers and nine verifiers run on every resource. A missing display label, an audit store that cannot take a row, a version column that disagrees with its declaration: each stops the compile with a named cause. Most libraries in this space fail at render time on the first unlucky page.

lib/ash_quick.ex:946
Strong

One source of truth per fact

The URL path is declared once in the router and read back as an assign. PubSub topics come from one module used by both the publisher and the subscriber. The wire prefix is separate from the display name so renaming a heading cannot move a topic. These choices remove whole classes of drift bugs.

Strong

Authorization is asked of Ash, not reimplemented

Reads and writes go through scope:, bulk writes force authorize?: true, and a hidden column is decided by Ash.can_see_fields. The UI only decides what to show; the action's policy decides what runs. Comments say this explicitly where it matters.

lib/ash_quick/liveview/list_utils.ex:820
Could be better

Event handling is three named hooks swapped on every navigation

List, details and form each detach and re-attach :quick_view_events_hook, :quick_view_info_hook and :quick_view_async_hooks inside handle_params. It works, and it leaves the host free to define its own handle_event. But which code handles an event depends on the last patch, which is invisible when reading any one file. A single dispatcher keyed on the current surface, or LiveComponents per surface, would make the flow traceable and remove the risk of a hook left attached after a failed transition.

lib/ash_quick/liveview/list_utils.ex:54, form_utils.ex:32, details_utils.ex:25
Could be better

The QuickView macro generates render/1 clauses and customisation by function name

Custom action templates are found by building action_<name>_html with String.to_atom at render time, and lifecycle hooks are private functions (after_mount, after_handle_params) the user overrides by pattern matching. Convention by name is easy to mistype with no error. Declaring templates and hooks as options (checked at compile time, like everything else here) would match the rest of the library's philosophy.

lib/ash_quick/liveview/quick_view.ex:692
Could be better

Configuration is global and partly compile-time

AshQuick.Config exposes around 30 application-env keys. :endpoint and :actor_resource are read with compile_env, and several others (audit store, storage, nav) are single global values. That is a singleton design: one endpoint, one actor resource, one storage per VM. It rules out umbrella apps with two web endpoints or an admin area with a different actor type. Per-resource overrides exist for audit; the same pattern for storage and endpoint would lift the limit.

lib/ash_quick/config.ex:223, :478
Could be better

Filters are stringly typed

Preset filters are maps with string keys (%{"name" => ..., "expression" => ...}) matched with Enum.find. Everything else in the options is validated structs. A small struct or keyword schema here would catch a misspelt key at compile time.

lib/ash_quick/liveview/list_utils.ex:116
Note

Offset pagination only

Lists page with limit and offset. That is the right default for a back-office table with page numbers. It is covered under Performance for large tables.

Aspect 3

Security

This is the most carefully built part of the library. I looked for the usual LiveView mistakes (atoms from user input, raw HTML, trusting hidden UI, path traversal, forged events) and found each one already handled. What remains are a few gaps around export and some defaults that depend on the host getting configuration right.

Strong

The usual injection routes are closed

No raw/1 anywhere in lib. Every atom from a URL goes through String.to_existing_atom with a rescue that keeps the string. No binary_to_term, no Code.eval. URL filters are applied with Ash.Query.filter_input, which honours field policies, and rows naming a field the actor cannot see are dropped before the query runs.

lib/ash_quick/liveview/url_params.ex:58, list_utils.ex:128
Strong

File serving is defensive

Keys are rejected if they contain .., empty segments, backslashes, NUL or a colon. Private objects need a Phoenix.Token bound to the exact key, with a default one-hour life. Responses carry nosniff, a sandboxing CSP, and SVG is never served inline. Writes go to a temp file and are renamed into place.

lib/ash_quick/storage/served.ex, storage/local.ex
Strong

Forged events are refused by the action, not the menu

Bulk actions only run over rows already on the page, read through the actor's scope, and force authorization even when a host domain is :when_requested. Impersonation and session revocation re-check the actor on every event.

Strong

Security tooling runs in CI

Sobelow at the :low threshold, mix deps.audit and hex.audit fail the build. Dependency floors in mix.exs are pinned above named CVE fixes, with the reason written next to each.

Risk

CSV and Excel exports do not neutralise formulas

String values are written to the file unchanged. A record whose name is =HYPERLINK(...) or starts with +, - or @ becomes a live formula when a colleague opens the export in Excel. This is the standard CSV-injection issue and back-office exports are its usual home. Prefixing such cells with a single quote (or a tab) for CSV, and forcing string cell type for xlsx, closes it.

lib/ash_quick/liveview/export_utils.ex:91
Risk

Export has no ceiling

An export streams the whole filtered table with timeout: :infinity, writes it to a temp file and uploads it. There is no row cap, no per-user concurrency limit and no rate limit, and starting a second export does not obviously cancel the first. One user (or one compromised account) clicking Export on a large table repeatedly can tie up database connections and disk. A configurable row limit and one running export per socket would bound it.

lib/ash_quick/liveview/export_utils.ex:64, list_utils.ex:498
Could be better

Exporting selected rows skips the base filter and trusts client ids

Bulk actions intersect the ticked ids with the rows on the page. Export does not: it takes ids straight from the form event and queries id in ^ids without base_filter or the preset filters. The read still runs under the actor's policies, so this is not a bypass of Ash authorization. But a host that uses base_filter to keep a view to "my shop's orders" will find a forged event can export other rows the policy happens to allow. Use the same selected_records intersection, or apply the base filter in both branches.

lib/ash_quick/liveview/list_utils.ex:446
Could be better

Exports are never deleted and their links are bearer tokens

Each export is stored under exports/<actor id>/ with a timestamped name, and nothing removes it. The docs say so and tell the host to clean up. A full data dump per click that lives forever is a liability by default; a built-in sweeper or an expiry on the object would make the safe behaviour the default one. The download link works for anyone who has it for an hour.

Could be better

Silent degradation when the host is misconfigured

If the socket lacks :peer_data or :x_headers, audit rows record no IP and nothing errors. With {:header, name} the client IP is whatever the last proxy hop wrote, which is correct only behind a trusted proxy. The library provides mix ash_quick.check and violation helpers to catch these, which is the right tool, but it relies on the host running them. A boot-time warning would catch the hosts that do not.

lib/ash_quick/liveview/mount.ex:128
Note

Audit writes bypass authorization by design

The audit store is written with authorize?: false inside the audited transaction, and the docs tell the host to keep that resource free of policies. That is correct for writing. It means reading the audit store is entirely the host's job to protect, and it holds attribute values, so it deserves the strictest read policy in the app.

lib/ash_quick/audit/store.ex:85
Note

Limits of this review

I read the storage, export, list, mount and session code paths closely and grepped the rest. I did not audit the S3 proxy's request signing, the impersonation token lifecycle or the upload path line by line. Those three deserve a dedicated pass.

Aspect 4

Performance

Sized correctly for what it is: a back-office tool with tens of rows per page and tens to hundreds of concurrent users. Several earlier hot spots have clearly been found and fixed. Nothing here is measured, though, and the paths that will hurt first on big tables are counting, offset paging and export. This section is from reading code; I ran no benchmarks.

Strong

Live updates are targeted and coalesced

A list subscribes to the topics of the records it is showing (and records related to them), not to the whole resource. Unrelated writes cost a viewer nothing. Refetches are held to one per five seconds by default, so a burst of writes becomes one query per viewer.

lib/ash_quick/liveview/liveness.ex:85
Strong

Permission checks are lazy

Row actions are resolved with Ash.can? only for the row whose menu is open, where an earlier version paid for every row on every render. Hidden columns are decided once per page with one can_see_fields call. Dropdowns read with count: false and select only the key and label.

lib/ash_quick/liveview/list_utils.ex:896
Strong

Page size is clamped on the server

?limit=100000 is held to the action's max_page_size, and a list action without a default limit does not compile.

Could be better

Every page read also counts the table

The pager shows total pages, so each load and each live refetch runs a COUNT with the same filters. On a table with millions of rows and a non-indexed filter this is slower than the page itself. An option for a count-free pager (next and previous only), or a cached or capped count, would be the first thing I would add for large resources.

lib/ash_quick/liveview/components/list_view.ex:641
Could be better

Offset paging and free-form sort and filter

Deep pages cost a scan of everything before them, and users can sort or filter by any offered column whether or not an index backs it. This is normal for admin tools. The library could help by letting a resource declare which columns are sortable and filterable by default being opt-in, or by documenting the index each one needs.

Could be better

Rows live in assigns, and the live graph walk can be wide

List results are kept as full records in socket assigns with all their loads, and re-sent on refetch. LiveView streams would cut memory and diff size. With recursive?: true (the default) the socket subscribes to one topic per record and per related record on the page, so a page of 100 rows with three relationships each holds a few hundred subscriptions. Fine at this scale, worth knowing about.

Could be better

Audit adds a write to every write

Each audited action computes a diff and inserts an audit row inside the same transaction. That is the correct trade for correctness. For bulk actions it means one audit insert per record on the :stream strategy, so a 10,000-row bulk update is 20,000 statements in one long transaction. Atomic bulk updates would be much faster but would lose the per-row diff.

Note

No telemetry of its own, no benchmarks

I found no :telemetry events for list reads, exports or refetches, and no benchmark suite. Ash's own telemetry covers the queries, but a host cannot easily see "which QuickView is slow". Two or three spans would make the points above measurable instead of argued.

Aspect 5

Complexity

The code is unusually well explained and unusually large. About a third of lib/ is documentation and comments, and those comments give reasons, which is rare and valuable. The cost is that the real size (around 20,000 lines of code after comments) sits in a handful of very large modules, maintained by one person.

6.2klines of @doc and @moduledoc
3.4klines of # comments
~20klines of actual code
1,735lines in the largest file
Strong

Comments explain why, and name the failure they prevent

Almost every non-obvious line carries the reason it exists and what breaks without it. For a library built on Ash and LiveView internals this is what makes the code maintainable at all. It also means decisions can be revisited, because the constraint is written down.

Strong

Module boundaries follow features

Each DSL section has its own directory with a transformer, a verifier and an info module. You can find where a behaviour lives from its name.

Could be better

Five modules hold most of the hard logic

form_utils.ex (1,735 lines, 165 functions), quick_view.ex (1,257), filter_form.ex (965), list_utils.ex (924) and custom_filter.ex (870). The *_utils names are a sign: these are not utilities, they are the list, details and form controllers. form_utils in particular mixes form building, uploads, nested forms, validation, submit and error wording. Splitting it by those concerns would shrink the blast radius of a change.

Could be better

Heavy reliance on other libraries' edge behaviour

Many comments describe a specific quirk of Spark, Ash, AshPhoenix or LiveView that the code works around (transformer ordering, when Spark validates options, what keep_live replaces, how bulk results wrap errors). Each is a place an upstream minor release can break. The version floors in mix.exs show this has already happened several times. Contributing the fixes upstream, where possible, would retire workarounds for good.

Could be better

The prose is dense and has a house style that slows reading

The comments are correct but often written as compressed aphorisms ("the menu decides what shows, not what runs"). A new contributor has to decode them. Plainer sentences, and moving long rationale into a small set of design notes linked from the code, would keep the reasons and lower the reading cost. The README at 1,336 lines and a 1,614-line changelog at version 0.1.0 have the same issue: complete, and hard to enter.

Risk

One author

Every commit in the history available to me is by one person. With this much surface and this much subtle upstream coupling, that is the largest practical risk to the project, larger than any code issue on this page.

Aspect 6

Tests

Strong, and structured sensibly in two tiers. I ran the library suite: 863 passed (859 tests, 4 doctests) in 26.6 seconds, no failures. The gaps are in kinds of testing, not in amount.

863library tests, all passing
~614example-app tests (not run here)
1.08 : 1test lines to lib lines, both tiers
4Elixir/OTP pairs in CI
Strong

Two tiers, each testing what it can honestly test

The library suite covers verifiers, parsers, storage and components without a database. The example app is a real Phoenix and Postgres host where around 50 scenario tests drive QuickViews end to end: optimistic locking reaching SQL, audit rows in the transaction, tenancy, uploads, impersonation. This is the right split.

Strong

Adversarial tests exist

hostile_params_test, attachment_forgery_test, private_actions_scenario_test, hidden_fields_scenario_test and page_ceiling_test test what an attacker would try, not only what a user would do. Every verifier has its own test file for the compile errors it raises.

Strong

CI is thorough

Warnings as errors, format, Credo, Sobelow, dependency audits, gettext catalogue freshness, Spark formatter freshness, and the library's own ash_quick.check --strict against the example app.

Could be better

The critical behaviour is only tested in the example app

The tests that prove the library works against a database live in example/, which is not in the Hex package and not what mix test runs at the root. A contributor who runs the root suite sees green without exercising a single real query. Making the root mix test fail loudly without the example suite, or documenting one command that runs both, would close that.

Could be better

No property-based tests where they would pay most

The URL parameter parser, the custom filter builder and the storage key validator are all pure functions over hostile input with round-trip properties (parse then print gives the same URL; no accepted key escapes the root). These are ideal for StreamData and are currently covered by examples only.

Could be better

About a third of library test files are not async

23 of 67 test files run synchronously and account for 21.6 of the 26.6 seconds. Most are likely sync because they touch application env. Passing config explicitly where possible would let them run in parallel and would also loosen the global-config coupling noted under Design.

Could be better

No browser-level or JavaScript tests

The 234 lines of JavaScript (print, locale, browser session) and the live_select interactions are untested by anything that runs a browser. LiveViewTest cannot see a broken hook. A handful of Playwright smoke tests over the example app would cover print, upload and the dropdowns.

Note

Coverage and the example suite

Coverage is configured with ExCoveralls in the example app. I did not run the example suite or verify what its coverage number includes, so I am not quoting one.

Aspect 7

Everything else

Strong

Developer experience is a first-class feature

An Igniter installer, generators for resources and QuickViews, a compliance check a host can run in CI, usage rules and skills for coding agents, and error messages that include the fix. Few 0.1.0 libraries ship this.

Strong

Internationalisation is built in

Gettext throughout, a translation template with a freshness check, right-to-left icon handling, per-reader timezones and locale carried into background export tasks.

Could be better

Versioning and stability signals

The changelog shows many breaking changes (feat!, refactor!) while the version stays 0.1.0. If anyone outside the source app depends on this, they cannot tell which commit is safe. Tagging releases, even 0.x ones, and marking which modules are public API (most internals are already @moduledoc false, which is good) would make it adoptable.

Could be better

Styling and markup are fixed

The components render the library's own HTML and Tailwind classes. I did not find a theming layer or a way to swap a component for the host's design system short of custom templates. For a tool extracted from one app that is expected. For general adoption it is usually the first thing people ask for.

Could be better

Accessibility was not assessed and is not tested

I saw no accessibility checks in the suite. Modals, dropdowns and data tables are the hard cases. Worth an audit pass with a screen reader and an automated checker.

Note

Documentation is complete and front-loaded

Everything is documented, mostly in moduledocs, and the README says so. There is no short path for a newcomer: a ten-minute tutorial that ends with a working page, before the reference, would do more for adoption than any feature.
